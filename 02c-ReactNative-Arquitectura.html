Arquitectura Enterprise

1. ¿Cómo organizarías una app enterprise?

Principios:

  • Feature modules autocontenidos con API clara hacia afuera.
  • Shared kernel — design system, networking, auth, utils.
  • Boundaries enforced — ESLint import rules, Nx module boundaries.
  • Testing pyramid — unit en domain, integration en features, E2E en critical paths.
  • Observability desde día 1 — logging, crash, performance budgets.
  • Documentación — ADRs, onboarding README, diagramas de navegación y data flow.

2. ¿Feature-based folders o layer-based?

Feature-based (preferido en mobile): features/checkout/ contiene screens, hooks, components, api de checkout. Escala con equipos (ownership por feature) y reduce cross-feature coupling.

Layer-based: screens/, components/, services/ — todo mezclado, carpetas gigantes, imports cruzados.

Híbrido común: feature-based + shared/ layer para código transversal. Evitar “big ball of mud” en components/ con 200 archivos.

3. ¿Dónde poner lógica de negocio?

  • Domain layer — funciones puras: validaciones, cálculos, reglas (testeables sin React).
  • Custom hooks — orquestación React-specific (useCheckout, useCart).
  • NO en components de UI — screens delgadas, presentational vs container.
  • NO en Redux reducers si es lógica compleja — extraer a domain services invocados por thunks.

Clean Architecture adaptada: entities/use cases en TS puro; adapters (API, storage); UI en React.

4. ¿Cómo desacoplás networking?

  • Cliente HTTP único (axios/fetch wrapper) con interceptors, base URL, auth injection.
  • API modules por dominio: userApi.getProfile() — screens no conocen URLs.
  • TanStack Query como capa de cache/sync — hooks useUserProfile() consumen API.
  • Tipos compartidos (OpenAPI codegen, Zod schemas).
  • Mock layer para tests y desarrollo offline (MSW).

5. ¿Cómo manejás dependency injection?

En frontend/mobile DI es más ligero que en backend:

  • React Context para servicios (ApiClient, Analytics) — test con providers mock.
  • Constructor injection en hooks — useAuth(authService) en tests.
  • Module factories — exportar singleton configurable en app bootstrap.
  • Evitar service locator global sin interfaces — dificulta testing.

Librerías como Inversify existen pero son raras en RN; Context + composition suele alcanzar.

6. ¿Cómo evitás tight coupling?

  • Import rules: features no importan internals de otras features — solo public API (features/auth/index.ts).
  • Event bus / navigation params con IDs, no objetos acoplados.
  • Interfaces para servicios externos (storage, analytics).
  • Evitar singletons mutables globales.
  • Code review enfocado en dependency direction (hacia adentro del dominio).

7. ¿Cómo harías una app escalable?

  • Modularización por feature con equipos aligned.
  • Design system compartido — consistencia y velocity.
  • State strategy clara (local vs server vs global).
  • CI/CD con builds paralelos, lint, tests, size budgets.
  • Feature flags para releases incrementales.
  • Performance budgets en listas y startup.
  • Monorepo si múltiples apps white-label comparten código.
  • Deuda técnica visible y tiempo asignado por sprint.

8. ¿Qué decisiones arquitectónicas tomaste en trabajos anteriores?

Prepará 2-3 historias con formato STAR:

  1. Contexto — tamaño del equipo, app, constraints.
  2. Decisión — ej: migrar de Redux clásico a RTK Query; adoptar Expo + EAS; feature-based refactor.
  3. Trade-offs — qué sacrificaste y por qué.
  4. Resultado — métricas (build time -40%, crash rate, velocity).

Ejemplo: “Separamos server state (React Query) de UI state (Zustand) porque Redux tenía 80% boilerplate de cache manual y re-renders en cada fetch.”
