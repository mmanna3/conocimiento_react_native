React Native — General

1. ¿Cómo funciona React Native internamente?

React Native permite escribir la lógica de la app en JavaScript mientras renderiza componentes nativos reales en iOS y Android.

React corre sobre un runtime JS como Hermes y mantiene un árbol de componentes que luego React Native traduce a vistas nativas.

La arquitectura vieja usaba un Bridge asíncrono entre JavaScript y nativo; la nueva arquitectura usa JSI y TurboModules para una comunicación más directa y eficiente.

La UI se renderiza en threads nativos separados del thread de JavaScript, por eso los problemas de performance suelen aparecer cuando el JS thread se bloquea con renders pesados o lógica costosa.

2. ¿Qué corre en JS thread y qué corre nativamente?

JS thread: React render, lógica de negocio, fetch, state management, la mayoría de handlers de eventos (onPress → JS → vuelve a nativo).

Native/UI thread: Layout (Yoga), composición de vistas, gestos de bajo nivel, animaciones nativas/Reanimated worklets en UI thread, rendering a pantalla.

Shadow thread (legacy architecture): cálculo de layout en thread separado.

Regla: operaciones pesadas en JS bloquean respuesta a taps y navegación. Mové trabajo pesado a nativo, workers, o chunk con InteractionManager.

3. ¿Qué es el bridge?

El bridge es la capa de comunicación asíncrona entre JS y código nativo en la arquitectura clásica de RN. Los módulos nativos y el UI manager envían mensajes serializados (JSON) en batches a través de una cola.

Limitaciones: overhead de serialización, asincronía (difícil llamadas síncronas), no compartir memoria, cuellos de botella con muchos eventos (scroll, animations driven by JS).

La New Architecture lo reemplaza con JSI + Fabric + TurboModules para invocaciones directas y lazy loading de módulos nativos.

4. ¿Qué cambió con la New Architecture?

  • JSI (JavaScript Interface) — JS puede invocar objetos C++ nativos directamente, sin bridge JSON.
  • Fabric — nuevo renderer: shadow tree en C++, layout más predecible, soporte Concurrent React, synchronous updates donde aplica.
  • TurboModules — módulos nativos cargados lazy, tipados con Codegen.
  • Codegen — genera bindings type-safe entre JS y nativo desde specs TypeScript/Flow.

Beneficios: menor latencia JS↔native, mejor performance en startup y listas, camino hacia shared memory y APIs más ricas. Migración gradual con compat layer; librerías third-party deben actualizarse.

5. ¿Qué son Fabric y TurboModules?

Fabric es el renderer de la New Architecture. Reemplaza al UIManager legacy. Maneja creación/actualización de shadow nodes en C++, integración con Yoga layout, y commit de mutaciones al host view de forma más eficiente. Habilita features de React 18 (Suspense, Concurrent rendering) en RN.

TurboModules reemplazan NativeModules clásicos. Se cargan bajo demanda (no todos al startup), usan JSI para invocación directa, y se generan con Codegen desde una spec (NativeModuleSpec).

6. ¿Qué problemas reales de performance encontraste?

Ejemplos típicos (personalizá con tu experiencia):

  • Scroll janky por re-renders en cada item de FlatList.
  • Animaciones en JS thread compitiendo con gesture handlers.
  • Imágenes full-resolution sin resize → memory pressure en Android.
  • Hydration de state pesado al montar screens en el stack de navegación.
  • Bridge saturado por analytics/logging excesivo en scroll events.

Framework STAR: Síntoma → Trace (Flipper/Systrace) → Acción → Resultado medible.

7. ¿Cómo optimizás una app RN?

  • FlatList/FlashList bien configuradas; evitar ScrollView con miles de items.
  • Reanimated 2+ para animaciones en UI thread.
  • Memoización estratégica; state local; evitar contextos globales calientes.
  • Hermes habilitado; ProGuard/R8 en Android; strip dead code.
  • Imágenes: tamaño correcto, cache (FastImage, expo-image), WebP donde aplique.
  • Defer work con InteractionManager.runAfterInteractions.
  • Reducir work en mount de screens (lazy tabs, skeleton first).
  • Monitorear JS thread FPS y native memory en CI/device farm.

8. ¿Qué diferencia hay entre Expo y bare React Native?

Expo — toolchain integrado: SDK con módulos preconfigurados, EAS Build/Submit/Updates, config plugins, managed workflow o dev client. Menos fricción inicial, OTA updates, builds en cloud.

Bare RN — control total de ios/ y android/, cualquier módulo nativo sin esperar soporte Expo, más setup manual (Xcode, Gradle, signing).

Hoy la línea se difuminó: Expo con dev client + config plugins permite casi cualquier módulo nativo. Muchos proyectos enterprise usan “Expo bare” o prebuild.

9. ¿Cuándo elegirías Expo?

  • Equipos que quieren ship rápido sin especialista nativo dedicado.
  • OTA updates, EAS Build, CI simplificado.
  • App que encaja en el SDK de Expo (cámara, location, notifications, etc.).
  • Prototipos, MVPs, apps de contenido/negocio estándar.

Elegiría bare cuando: módulos nativos muy custom, requisitos de binary size extremos, integraciones legacy específicas, o políticas de build 100% on-premise sin EAS.

10. ¿Cómo manejás deep linking?

Configuración en tres capas:

  1. Nativo — URL schemes, Universal Links (iOS), App Links (Android) en Info.plist / AndroidManifest.
  2. React Navigation — linking config mapeando paths a screens y params.
  3. Runtime — escuchar URL inicial (Linking.getInitialURL) y eventos (Linking.addEventListener).

Consideraciones: auth gates (redirect a login si no hay sesión), deferred deep links, state restoration, testing en cold/warm start. Expo Router simplifica file-based routing + linking.

11. ¿Cómo manejás navegación?

React Navigation es el estándar de facto: stack, tab, drawer navigators. Alternativas: Expo Router (file-based sobre React Navigation), React Native Navigation (Wix, nativo).

Patrones enterprise:

  • Typed navigation con TypeScript (RootStackParamList).
  • Separar auth flow vs app flow (root navigator condicional).
  • Deep linking unificado.
  • Lazy loading de stacks por feature.
  • Evitar pasar objetos grandes en params — pasar IDs y fetch en destino.

12. ¿Cómo manejás estados globales?

Separar por tipo:

  • Server state — TanStack Query / RTK Query (cache, stale, refetch).
  • Client global — Zustand o Redux Toolkit según complejidad y equipo.
  • UI efímera — state local o context acotado (modal open, form draft).
  • Auth/session — context + secure storage; tokens fuera de Redux si no hace falta.

Evitar un store monolítico. Feature slices con selectors memoizados. Persistir solo lo necesario (redux-persist, MMKV).

13. ¿Cómo estructurás un proyecto RN grande?

Feature-based con shared layer:

src/
  features/        # auth, home, payments — screens, hooks, components locales
  shared/          # ui kit, utils, api client, types
  navigation/
  store/           # si Redux global
  app/             # providers, entry

Monorepo (Nx/Turborepo) si hay múltiples apps o packages compartidos. Barrel exports con cuidado (tree-shaking). Absolute imports con path aliases. Documentar ADRs para decisiones arquitectónicas.

14. ¿Cómo manejás configuración por ambientes?

  • .env + react-native-config o Expo app.config.js con extra.
  • Schemes/flavors: dev, staging, prod con bundle IDs distintos (instalación side-by-side).
  • Build-time injection via CI (EAS env secrets, GitHub Actions).
  • Nunca commitear secrets — solo URLs públicas y feature flags no sensibles.

15. ¿Cómo manejás secrets?

Regla de oro: nada verdaderamente secreto en el bundle JS — es reverse-engineerable.

  • API keys de cliente: restricción por bundle ID / certificate pinning / proxy backend.
  • Tokens de usuario: Keychain (iOS) / EncryptedSharedPreferences o Keystore (Android) via react-native-keychain o Expo SecureStore.
  • Secrets de build: EAS Secrets, GitHub encrypted secrets, Vault.
  • OAuth: PKCE, refresh token rotation, backend como BFF.

16. ¿Cómo debuggeás crashes nativos?

  • Symbolicated stack traces — dSYM (iOS), mapping/proguard (Android).
  • Reproducir en debug con Xcode/Android Studio attached.
  • Flipper crash reporter, logcat, Xcode Organizer crashes.
  • Bisect: ¿crash en release only? → optimizaciones ProGuard, Hermes, diferencias de config.
  • Sentry/Firebase Crashlytics con breadcrumbs y contexto de navegación.

17. ¿Cómo manejás memory leaks?

  • Cleanup en useEffect return: listeners, subscriptions, timers.
  • Cancelar fetch/axios con AbortController al unmount.
  • Evitar referencias globales a screens desmontados.
  • Navigation: unmountOnBlur donde aplique; no acumular listeners en focus sin blur cleanup.
  • Imágenes: liberar cache cuando crece (expo-image tiene políticas).
  • Profiling periódico con Instruments / Android Profiler en flows críticos.

18. ¿Cómo manejás permisos?

Usar librerías unificadas: react-native-permissions o APIs de Expo (expo-camera, expo-location).

Patrón UX:

  1. Explicar por qué antes del diálogo del sistema (pre-prompt screen).
  2. Pedir permiso en contexto (al tap “Escanear QR”, no al abrir app).
  3. Manejar denied, blocked → deep link a Settings.
  4. iOS Info.plist usage descriptions obligatorios; Android 13+ notification permission runtime.

19. ¿Cómo manejás lifecycle/backgrounding?

AppState de React Native: active, background, inactive.

  • Pausar polling/video en background.
  • Flush analytics queue antes de background.
  • Refresh token / sync al volver a active.
  • iOS: background modes limitados (audio, location, fetch); Android: WorkManager para tareas diferidas.
  • Guardar draft de forms en background si el OS puede matar el proceso.

20. ¿Cómo manejás reconnect/offline?

  • @react-native-community/netinfo para detectar conectividad.
  • TanStack Query: onlineManager, retry, refetch on reconnect.
  • Cola de mutaciones offline (optimistic updates + persist + replay).
  • UI clara: banner offline, estados degradados, cache stale con timestamp.
  • Conflict resolution strategy documentada (ver offline storage).

21. ¿Cómo hacés release management?

  • Versionado semántico + build number auto-incrementado en CI.
  • Branches: trunk-based o gitflow lite; release branches para hotfixes.
  • TestFlight / Internal Testing → staged rollout (10% → 50% → 100%).
  • Changelog automatizado (conventional commits).
  • Feature flags para activar post-release.
  • EAS Submit / Fastlane para stores; checklist pre-release (QA sign-off, crash-free rate baseline).

22. ¿Cómo investigás un crash en producción?

  1. Crashlytics/Sentry → stack trace symbolicado, versión, device, OS.
  2. Filtrar por release, % usuarios afectados, si es nuevo o regresión.
  3. Breadcrumbs: última screen, acciones, API calls.
  4. Reproducir con mismos params/device; si no, binary search en commits.
  5. Hotfix branch si es crítico; staged rollout del fix.

23. ¿Cómo monitoreás apps mobile?

Capas:

  • Crashes — Sentry, Firebase Crashlytics, Bugsnag.
  • Performance — Firebase Performance, Datadog RUM, custom traces.
  • Analytics — Amplitude, Mixpanel, Firebase Analytics.
  • Logs — structured logging en dev; en prod solo eventos clave (no PII).
  • Health KPIs — crash-free sessions, ANR rate (Android), app start time, API error rates.

24. ¿Qué herramientas usaste para analytics/crash reporting?

Mencioná las que hayas usado con profundidad. Combo típico enterprise:

  • Sentry — errors JS y nativos, releases, performance.
  • Firebase Crashlytics — crashes nativos, gratuito, integración Google.
  • Amplitude/Mixpanel — product analytics, funnels.
  • Datadog — si ya está en el stack backend.

Importante: sampling, GDPR/consent, no loguear PII, correlacionar con release version y feature flags.

25. ¿Cómo reducirías el tamaño de una app?

  • Hermes; enable ProGuard/R8; shrink resources (Android).
  • App Bundles (AAB) con splits por ABI/density.
  • Auditar dependencias (bundle analyzer, npx depcheck).
  • Imágenes vectoriales (SVG) o WebP; eliminar assets no usados.
  • Lazy require de features pesadas; evitar importar lodash entero.
  • iOS: bitcode off (deprecated), strip symbols en release, On Demand Resources si aplica.

26. ¿Cómo manejás feature flags?

  • Servicios: LaunchDarkly, Firebase Remote Config, Unleash, flagsmith.
  • Fetch al startup + cache local; refresh periódico o on foreground.
  • Defaults seguros si el fetch falla (fail closed o open según riesgo).
  • Tipado de flags; eliminar flags muertos (deuda de flags).
  • Combinar con staged rollout en stores para riesgo dual.

27. ¿Cómo hacés code splitting/lazy loading?

En RN no hay dynamic import nativo como web webpack chunks, pero podés:

  • Lazy screens con React Navigation (React.lazy + Suspense limitado en RN).
  • Requerir módulos pesados solo cuando se necesitan (require() dentro de handler).
  • Separar bundles OTA (Expo Updates con assets).
  • Monorepo: packages por feature importados solo donde se usan.

El bundle principal sigue siendo un JS bundle — el win es startup time y memory, no descarga on-demand como web.

29. ¿Qué es Yoga?

Yoga is an embeddable layout system used in popular UI frameworks like React Native. Yoga itself is not a UI framework, and does not do any drawing itself. Yoga's only responsibility is determining the size and position of boxes.

Yoga supports a familiar subset of CSS, mostly focused on Flexbox. This gives users a familiar model, and enables sharing code between native platforms and the browser.
