OTA Updates

1. ¿Qué experiencia tenés con CodePush/EAS Updates?

Microsoft CodePush (App Center): OTA de JS bundle para RN bare. Check update on launch, download en background, apply on restart o immediate.

EAS Update (Expo): canal-based (production, staging), integrado con EAS Build runtime versioning, rollback desde dashboard.

Experiencia típica a describir:

  • Configurar runtime version policy (appVersion vs fingerprint).
  • Canales por ambiente; staged rollouts.
  • CI publica update en merge a release branch.
  • Monitoring post-deploy; rollback cuando error rate sube.

Limitación común: no puede cambiar código nativo — solo JS/assets compatible con binary existente.

2. ¿Qué riesgos tienen los OTA updates?

  • Breaking native mismatch — update JS incompatible con binary → crash on launch. Mitigar: runtime versioning estricto.
  • Store policy — Apple restringe OTA que cambie “purpose” de app; bugfix JS generalmente OK, feature major discutible.
  • Sin review de Apple/Google — bug en OTA llega instantáneo a todos → necesitás rollback rápido y staged rollout.
  • State/schema migrations — persist incompatible post-update.
  • Security — canal de update comprometido = supply chain risk — firmar updates, HTTPS, auth.
  • Testing gap — OTA no pasó store QA — requiir mismo CI gates que release.

Best practices: canary cohorts, automatic rollback on crash spike, never OTA native dep changes, feature flags dentro del bundle OTA.
