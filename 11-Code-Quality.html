11 · Code Quality

Calidad de código

1. ¿Qué buscás en un PR review?

  • Correctness — lógica, edge cases, error handling.
  • Architecture — responsabilidades, coupling, ubicación del código.
  • Performance — re-renders, listas, memory leaks.
  • Security — secrets, input validation, storage.
  • Tests — behavior covered, no brittle tests.
  • Readability — naming, size de funciones, comentarios solo donde aportan.
  • Consistency — patterns existentes del repo.

Priorizar blockers vs nits — distinguir must-fix de suggestions.

2. ¿Qué makes a good PR?

  • Scope pequeño y enfocado — una cosa por PR.
  • Descripción clara: qué, por qué, cómo testear.
  • Screenshots/video para cambios UI.
  • Tests incluidos o justificación explícita.
  • Self-review antes de pedir review.
  • Linked ticket/issue; migration notes si aplica.
  • CI green; no force-push caótico mid-review sin avisar.

3. ¿Qué anti-patterns detectás rápido?

  • God components de 500+ líneas.
  • useEffect para todo (fetch + transform + sync en un effect).
  • Prop drilling extremo sin justificación.
  • Any/types mentirosos; @ts-ignore sin comentario.
  • API calls directos en components sin capa de abstracción.
  • Optimización prematura (memo everywhere).
  • Copiar-pegar en lugar de abstraer con criterio.
  • Ignorar platform differences iOS/Android.

4. ¿Cómo discutís desacuerdos técnicos?

  • Data over opinion — benchmarks, POCs, trade-off doc.
  • ADRs para decisiones reversibles vs irreversibles.
  • Escuchar primero — entender constraints del otro.
  • “Disagree and commit” una vez decidido.
  • Timebox spikes para destrabar debates abstractos.
  • Escalar a tech lead/architect solo si deadlock — no como primera opción.

5. ¿Cómo mentoreás juniors?

  • Pair programming en tasks reales, no solo teórico.
  • PR reviews educativos — explicar el “por qué”, links a docs.
  • Delegar ownership incremental (feature end-to-end con soporte).
  • Safe space para preguntas — normalizar “no sé”.
  • 1:1s regulares — career, blockers, feedback bidireccional.
  • Compartir runbooks (debug RN, release process).

6. ¿Qué estándares de código te importan?

  • ESLint + Prettier enforced en CI.
  • TypeScript strict.
  • Conventional commits.
  • Import order, absolute paths, barrel exports controlados.
  • No merge con coverage drop en critical paths.
  • Husky/lint-staged pre-commit.
  • Documented folder structure y naming conventions.

7. ¿Qué opinás de clean architecture?

Útil como principio — separación de concerns, dependencias hacia adentro, domain independiente de UI/framework. En mobile frontend, adaptar pragmáticamente:

  • Domain/use cases en TS puro — sí.
  • 4 capas estrictas con 20 interfaces — overkill para pantalla CRUD.
  • El valor está en testabilidad y boundaries claros, no en ceremonia.

Feature folders + domain services + React Query suele ser suficiente “clean enough”.

8. ¿Qué opinás de SOLID en frontend/mobile?

  • S — componentes/hooks con una responsabilidad; evitar SmartComponent que hace todo.
  • O — extender via composition (variants) vs modificar componente base constantemente.
  • L — menos relevante sin herencia profunda; aplica a substituibility de implementations (mock API).
  • I — props interfaces pequeñas; no forzar consumers a pasar 20 props opcionales.
  • D — depender de abstracciones (ApiClient interface) no axios directo en 50 files.

SOLID guía, no religión — no crear AbstractFactory para un botón.

9. ¿Qué significa “maintainable code”?

Código que el equipo puede cambiar con confianza meses después:

  • Legible sin contexto del autor original.
  • Tests que permiten refactor.
  • Bajo acoplamiento — cambio localizado.
  • Convenciones consistentes — predictible dónde buscar cosas.
  • Complejidad proporcional al problema — no over-engineered.
  • Documentación mínima en decisiones no obvias (ADRs).

Maintainability = f(readability, testability, modularity, operability).
