UI / Rendering

1. ¿Qué componentes de RN generan problemas de performance?

  • ScrollView con muchos hijos — renderiza todo upfront.
  • FlatList mal configurada — sin memo en rows, keys malas, nested lists.
  • Animated (legacy) driven by JS en scroll/gestures.
  • Image sin dimensiones o resolución excesiva.
  • TextInput controlled con re-render de padre grande en cada keystroke.
  • MapView, WebView, Video — views nativas pesadas; múltiples instancias.
  • Shadows en Android — elevation costosa en listas.
  • BlurView, gradients complejos — overdraw.

2. ¿Cuándo usar FlatList vs ScrollView?

ScrollView: pocos hijos de altura acotada (formularios cortos, contenido estático). Renderiza todos los children de una vez — simple pero no escala.

FlatList: listas dinámicas o largas. Virtualiza: solo monta items visibles + buffer. Obligatorio para feeds, chats, catálogos.

FlashList (Shopify): alternativa más performante cuando FlatList no alcanza — recycling agresivo, mejor FPS en listas complejas.

Regla: si podés scrollear más de ~20-30 items repetitivos → FlatList/FlashList.

3. ¿Qué optimizaciones tiene FlatList?

  • keyExtractor con IDs estables.
  • getItemLayout — salta medición si altura fija.
  • initialNumToRender, maxToRenderPerBatch, windowSize — tunear memoria vs blank areas.
  • removeClippedSubviews (Android especialmente).
  • memo en item component; evitar inline renderItem closures (extraer componente).
  • extraData solo cuando el item no cambia referencia pero contenido sí.
  • Separar header/footer con props dedicadas, no como items fake.

4. ¿Qué problemas trae un keyboard handling malo?

  • Inputs tapados por el teclado — usuario no ve qué escribe.
  • Layout jumps / flickering al abrir/cerrar teclado.
  • Scroll incorrecto en forms largos.
  • Android vs iOS comportamientos distintos (adjustResize vs adjustPan).

Soluciones: KeyboardAvoidingView, react-native-keyboard-controller (recomendado moderno), KeyboardAwareScrollView, configurar android:windowSoftInputMode, dismiss keyboard on tap outside, scroll to focused input.

5. ¿Cómo manejás layouts responsive?

  • Flexbox — base de todo layout RN (ver pregunta 7).
  • useWindowDimensions / Dimensions para breakpoints.
  • Porcentajes y flex: 1 en lugar de pixels fijos.
  • Tablets: layouts alternativos (two-pane) con breakpoint hooks.
  • PixelRatio para bordes finos (hairlineWidth).
  • Probar rotación y split-screen (Android).

Evitar duplicar lógica iOS/Android salvo safe areas y platform quirks.

6. ¿Cómo manejás safe areas?

react-native-safe-area-context es el estándar:

  • SafeAreaProvider en root.
  • SafeAreaView o hook useSafeAreaInsets() para padding manual.

Insets cubren notch, status bar, home indicator, navigation bar Android (edge-to-edge). En modals y headers custom, aplicar insets top/bottom explícitamente. Con React Navigation, headerTransparent requiere manejo manual.

7. ¿Cómo funciona Flexbox en RN?

RN usa Yoga (subset de Flexbox). Diferencias clave vs web:

  • flexDirection default es 'column' (web es row).
  • Solo una dimensión flexible por eje — no hay flex-basis: auto idéntico a web en todos los casos.
  • No hay grid CSS nativo (usar librerías o flex tricks).
  • alignContent, flexWrap soportados; gaps en versiones recientes.

Patrón común: contenedor flex: 1, header/footer fijos, content flex: 1 scrollable. Debug con borders temporales y Flipper layout inspector.

8. ¿Qué diferencias hay entre RN styling y CSS web?

CSS WebReact Native
Stylesheets globales, cascadaStyleSheet objects, sin cascada — un estilo por view
Todas las unidadesSolo números (dp/pt), no px/em/rem/% limitado
display: grid, tableNo soportado nativamente
box-shadow complejoshadow* props iOS; elevation Android
:hover, :focusPressable states, no pseudo-selectors
inheritance de fontText no hereda estilos del padre Text automáticamente en todos los casos

Para web-like styling en RN: NativeWind (Tailwind), styled-components. Animaciones: Reanimated, no CSS transitions.
