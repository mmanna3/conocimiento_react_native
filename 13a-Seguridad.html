Seguridad

1. ¿Dónde guardar tokens?

  • Access token: memoria (variable) mientras app activa; al background prolongado, re-auth o refresh desde secure storage.
  • Refresh token: iOS Keychain / Android Keystore via react-native-keychain o Expo SecureStore.
  • Biometric gate opcional para reabrir tokens en apps financieras/salud.

Nunca: AsyncStorage plain, Redux persist sin encrypt, logs, analytics, query params.

2. ¿Qué NO guardar en AsyncStorage?

  • Refresh/access tokens.
  • Passwords o PINs.
  • PII sensible (SSN, tarjetas, datos médicos).
  • Encryption keys.
  • OAuth client secrets (no deberían estar en mobile anyway).

AsyncStorage es un plist/XML sin encrypt fuerte — asumí lectura en device comprometido.

3. ¿Qué es certificate pinning?

Validar que el certificado/TLS public key del servidor coincide con uno embebido en la app, en lugar de confiar solo en CAs del sistema. Mitiga MITM con rogue CA o corporate proxies maliciosos.

Implementación: ssl-pinning libraries, OkHttp CertificatePinner (Android), TrustKit (iOS). Cuidado: rotation de certs requiere app update o backup pins. Alternativa más mantenible: pinning via SPKI hashes con fallback.

Trade-off: más seguridad vs operacional complexity — común en fintech, banking.

4. ¿Qué riesgos mobile te preocupan?

  • Reverse engineering — extraer API keys, bypass client checks.
  • Insecure storage — tokens en plain text.
  • MITM — sin cert pinning en redes públicas.
  • Deep link hijacking — intent filters mal configurados.
  • Jailbreak/root detection — bypass de seguridad client-side.
  • Clipboard/logging leaks — passwords copiados.
  • WebView vulnerabilities — JS injection, mixed content.
  • Supply chain — deps npm comprometidas.

Defense in depth: secure storage, attestation (Play Integrity / DeviceCheck), backend validation, min permissions, obfuscation (R8) como speed bump no como única defensa.
