Redux

1. ¿Qué problema resuelve Redux?

Redux centraliza state global predecible con un flujo unidireccional: UI dispatch actions → reducers producen nuevo state → UI se suscribe.

Resuelve: state compartido complejo entre muchas pantallas, debugging con action log, time-travel, middleware para side effects, state predecible e inmutable.

No resuelve server cache bien por sí solo (ahí RTK Query); no reemplaza state local de forms.

2. ¿Cuándo NO usar Redux?

  • Apps pequeñas con poco state compartido → Context + useState alcanza.
  • Principalmente server state → React Query solo.
  • State efímero de UI (modal open) → local.
  • Equipo pequeño sin necesidad de devtools/time-travel.

Red flag: Redux para todo incluyendo API cache manual — mucho boilerplate sin beneficio.

3. ¿Qué diferencia hay entre Redux Toolkit y Redux clásico?

Redux clásico: switch-case reducers, action creators manuales, configureStore manual, mucho boilerplate, Immer no incluido.

RTK: createSlice (reducers + actions auto), configureStore con defaults (thunk, devtools), Immer built-in (mutación “sintáctica”), createAsyncThunk, RTK Query integrado.

RTK es el standard recomendado oficialmente — Redux clásico solo en legacy codebases.

4. ¿Qué es un reducer?

Función pura (state, action) => newState. Dado el state actual y una action tipada, devuelve el próximo state sin mutar el anterior.

Debe ser determinística — no fetch, no Date.now(), no random. Side effects van en middleware/thunks/listeners.

Con Immer (RTK), escribís lógica mutante que Immer traduce a updates inmutables.

5. ¿Qué significa que Redux sea immutable?

Cada transición produce un nuevo objeto state (shallow copy en el path cambiado). React-Redux compara referencias para decidir re-renders; mutación directa rompe change detection y time-travel debugging.

Immer facilita inmutabilidad sin spread hell: state.items.push(item) bajo hood es inmutable.

6. ¿Qué es un middleware?

Capa que intercepta actions entre dispatch y reducer. Cadena de funciones store => next => action => ....

Usos: logging, analytics, async (thunk), crash reporting, persist (redux-persist), custom authorization gates.

RTK configureStore incluye thunk por default; podés agregar custom middleware en el array.

7. ¿Cómo funciona Redux Thunk?

Middleware que permite dispatch de funciones además de plain objects. La función recibe (dispatch, getState) y puede hacer async:

dispatch(async (dispatch, getState) => {
  dispatch(setLoading(true));
  const data = await api.fetch();
  dispatch(setData(data));
});

RTK prefiere createAsyncThunk para estados pending/fulfilled/rejected estandarizados. Thunk sigue válido para lógica custom.

8. ¿Qué ventajas tiene RTK Query?

  • Cache automático, deduplicación, invalidation tags.
  • Loading/error states generados.
  • Hooks auto-generados: useGetUserQuery(id).
  • Optimistic updates, polling, prefetch.
  • Integración Redux DevTools.
  • Elimina 70%+ del boilerplate de fetch manual en Redux.

Compite con TanStack Query — RTK Query si ya tenés Redux; TanStack si querés server state sin Redux.

9. ¿Redux vs Context API?

ContextRedux
Built-in, simpleLib externa, más setup
Re-render todos consumersSelectors granulares con react-redux
Sin middleware/devtools avanzadosDevTools, middleware, ecosystem
Bien para theme, locale, auth simpleBien para state complejo frecuente

No son mutuamente excluyentes — Context para DI/theme, Redux/Zustand para app state denso.

10. ¿Cómo evitar over-rendering con Redux?

  • useSelector con selectors que retornan solo la slice necesaria.
  • createSelector (Reselect) para memoizar derivaciones.
  • Evitar selectores que retornan objetos nuevos cada vez.
  • Split slices — componentes suscritos solo a su dominio.
  • React.memo en hijos con props de Redux estables.
  • RTK Query hooks ya optimizan suscripciones por endpoint+args.

11. ¿Cómo estructurarías slices?

Por dominio de negocio, no por tipo técnico:

store/
  slices/
    authSlice.ts
    cartSlice.ts
  api/
    usersApi.ts   # RTK Query
  index.ts        # configureStore

Cada slice: state inicial, reducers sync, extraReducers para thunks, selectors colocados en el mismo file o selectors.ts. Normalizar entities relacionales (users byId) si hay relaciones complejas — o delegar a RTK Query cache.

12. ¿Qué errores comunes viste?

  • Guardar server data duplicado en slices cuando RTK Query ya cachea.
  • God slice con todo el state de la app.
  • Selectors no memoizados retornando { a, b } inline.
  • Side effects en reducers.
  • Mutación directa sin Immer en reducers legacy.
  • Over-engineering Redux para apps que solo necesitan React Query + Context.
