10 · Mobile Engineering

Producción y operaciones

1. ¿Cómo manejás releases graduales?

  • App Store / Play Console — phased rollout (1% → 100% over days).
  • Feature flags — código en prod pero feature off hasta activar por cohorte.
  • OTA (EAS Updates) — JS bundle a subset de runtime versions.
  • Monitorear crash-free rate y KPIs por cohorte antes de expandir.
  • Rollback plan documentado en cada release.

2. ¿Qué experiencia tenés con CI/CD?

Mencioná stack concreto: GitHub Actions / Bitrise / CircleCI / EAS Workflows.

  • PR: lint, typecheck, unit tests, optional Detox smoke.
  • Main: build artifacts, deploy staging, E2E nightly.
  • Tag release: signed builds, TestFlight/Internal track, submit stores.
  • Secrets management, caching, parallel jobs.

3. ¿Cómo manejás rollback?

  • Store rollback — pausar phased rollout; no podés “revertir” binary en stores — subís fix forward hotfix.
  • OTA rollback — republish bundle anterior en EAS/CodePush (rápido para bugs JS).
  • Feature flags — kill switch instantáneo sin nuevo binary.
  • Backend compatibility — versionar API para soportar N-1 app versions.

4. ¿Cómo monitoreás producción?

Dashboards y alertas:

  • Crash-free sessions / users (Sentry, Crashlytics).
  • ANR rate Android, slow renders.
  • API error rates, latency p95.
  • Business KPIs (conversion, retention) correlacionados con releases.
  • Alertas Slack/PagerDuty on SLO breach.

5. ¿Qué métricas mobile mirás?

  • Stability: crash-free rate, ANR, OOM kills.
  • Performance: cold start time, TTI, FPS scroll, bundle size.
  • Engagement: DAU/MAU, session length, retention D1/D7/D30.
  • Quality: app store rating, review sentiment, support tickets spike.
  • Release health: adoption rate of new version, error rate delta vs previous.

6. ¿Cómo investigás crashes?

  1. Triage: volume, severity, new vs regression, affected versions/OS.
  2. Symbolicate stack; identificar frame app vs third-party.
  3. Repro steps from breadcrumbs/user reports.
  4. Bisect commits si regresión reciente.
  5. Fix + test + hotfix release si P0.
  6. Postmortem si impacto alto — root cause, prevention.

7. ¿Cómo manejás hotfixes?

  • Branch hotfix/x.y.z desde tag de prod.
  • Fix mínimo — no scope creep.
  • Expedited QA en dispositivos críticos.
  • OTA si es JS-only; store expedited review si nativo.
  • Merge back to main; bump patch version.
  • Comunicar stakeholders timeline y riesgo.

8. ¿Cómo trabajás con QA?

  • Test plans por feature con acceptance criteria claros.
  • Staging builds automáticos por PR/merge.
  • testID para automatización; documentar edge cases.
  • Bug triage conjunto — severidad, repro, logs.
  • QA early en refinamiento — shift-left.
  • Device matrix acordado (iOS versions, Android OEMs).

9. ¿Cómo manejás deuda técnica?

  • Inventario visible (Linear/Jira label “tech-debt”).
  • 20% capacity por sprint o debt sprints per quarter.
  • Priorizar por interés (pain frequency × fix cost).
  • Boy scout rule en PRs tocados.
  • ADRs para no re-debatir; deprecations con deadline.
  • Metrics: build time trend, flaky tests, outdated deps count.

10. ¿Cómo priorizás bugs?

Matriz impacto × urgencia:

  • P0: crash loop, payment broken, data loss — hotfix inmediato.
  • P1: feature core degradada, muchos usuarios — next release.
  • P2: workaround exists, subset usuarios.
  • P3: cosmetic, edge case.

Factores: % usuarios afectados, revenue impact, reputación, costo fix, regresión vs pre-existing.

11. ¿Qué harías si una release rompe producción?

  1. Contener — feature flag off, pausar rollout, OTA rollback.
  2. Comunicar — stakeholders, status page si aplica.
  3. Diagnóstico — crashes, logs, diff vs previous release.
  4. Fix — hotfix mínimo; no mezclar features nuevas.
  5. Verificar — QA targeted, monitor metrics 24-48h.
  6. Postmortem — qué falló en proceso (tests, rollout, review).

Priorizar usuario y data integrity sobre culpa — blameless postmortem.
